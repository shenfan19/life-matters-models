# Modeling Methodology and Discipline Inclusion Criteria

## LM's Core Methodology: Coupling, Not Stacking

LM exists to put mechanisms that have each been validated independently in separate publications into a single model, so that mechanisms which had been scattered across different papers, each unaware of the other's existence, produce a real interaction and reveal a trade-off that lay outside the modeling scope of any single paper. This is the core value that distinguishes this project from reproducing a single study's conclusion paper by paper, and it is the sole criterion for judging whether a model should incorporate more mechanisms and whether an already-incorporated mechanism should be kept.

Whether a mechanism combination holds up is judged not by how many publications or existing models were mixed in, but by whether a pathway exists along which the mechanisms force a real trade-off on some decision variable. If a decision variable's benefit shows up on only one objective and carries no cost on any other objective, that mechanism remains isolated and does not constitute coupling, even if it sits next to three or five other equally isolated mechanisms and the model as a whole looks high-dimensional; no additional trade-off information is produced, and the Pareto front simply degenerates separately along several unrelated directions. Real coupling requires at least two mechanisms to share the same finite resource, or one mechanism's output to feed another mechanism's input, so that every improvement the optimizer makes on one objective forces a measurable cost on another.

On this basis, the number of mechanisms is neither an inclusion criterion nor a rejection criterion. A narrow, deep single-mechanism model, one that pins down a dynamic's coefficients and trajectory well enough to pass leave-one-out validation against measurements independent of the fitting data, reaches a level of evidence that a combined model, one that only validates internal self-consistency of a Pareto front, cannot reach by putting several mechanisms together; the two are parallel, equally valid validation goals that do not substitute for each other, and there is no one-directional requirement that a narrow model must be widened or that a wide model must be validated down to the narrow standard. Conversely, if a model already mixes multiple mechanisms and one of them has no real resource competition or causal pathway connecting it to the rest, the correct move is to remove it from the model rather than keep it to pad out the mechanism count. A dimension with no relationship to the rest of the model does not add information by staying in the model; it only adds decision variables, slows the search, and creates meaningless free drift in the front.

When adding to or reviewing a model, check it against these questions:

- Does this decision variable's benefit produce a corresponding cost on any other objective, or is it purely one-directional, more is simply better?
- If this decision variable is pushed to its boundary, do the other objectives get correspondingly worse, or are they entirely unaffected?
- Do the model's several mechanisms share the same finite resource, or does one mechanism's output feed into another mechanism's input?
- If a given mechanism were removed, would the front produced by the remaining mechanisms change at all? If not, should that mechanism be removed?

## Model Inclusion Criteria and Discipline Coverage Inventory (added 2026-07-29)

LM moves from "is a discipline or a claim worth modeling" through inclusion, evaluation, and output, three stages in sequence. This section covers the inclusion stage, deciding whether a direction is worth the modeling effort. The evaluation stage's six-step process, four-dimension attribution classification, and per-model determination are in `models/test_validation/validation_report.md`; the output stage means the paper cites only models confirmed in the evaluation stage, as covered in that file's "Paper Model Inventory" section, with selection conclusions classified by S1-S4.

The formal English statement of these four questions has been written into the Scope section of `docs/LM_format_1.0.md` (the Inclusion Test), as the format specification's own operational definition of what topics fall within the scope of LM format. This section's four questions, notation conventions, and inventory table are that definition's concrete application and ongoing tracking within this project's model library, not a separate standard.

### The Four-Question Screen

Inclusion judgment lands on four points where LM is actually used, each corresponding to a question about whether it holds up:

- **var**: does the discipline's claim carry a transferable, specific numeric value, an effect size, a rate constant, a dose-response coefficient, rather than only a directional description such as "has an effect" or "is associated"?
- **equ** (`equations`): does the mechanism have a recognized functional form, a differential equation, a regression equation, a kinetic equation, that can be encoded directly, without the modeler inventing a structure on the spot?
- **sim**: once encoded, can the mechanism produce a trajectory that evolves over time and can be compared against independent data points, rather than only a static numeric display?
- **opt**: does the discipline's decision space contain a real multi-objective trade-off, not a single optimum, worth running an optimizer over?

The first two questions, var and equ, decide whether a discipline's claim is worth encoding into LM at all; failing either means the material cannot support an executable model and is not worth the modeling effort. The latter two, sim and opt, decide how far the model can be used for once it is encoded; when var and equ pass but sim or opt cannot be used, the model still stands, only its use is limited to a mechanism-and-engine cross-check display rather than independent prediction or optimization (see the `confidence` scale definition in `docs/authoring/ratings.md`).

The "Attempted but Not Built" section of `models/test_validation/validation_report.md` records specific candidate-level examples, not whole-discipline examples, that this four-question screen has already ruled out, such as the Bass technology-diffusion model, rejected for untrustworthy p/q parameter sourcing, and Lanchester's square law, rejected because the original day-by-day force-strength data could not be obtained publicly; these serve as reference samples for how to apply the four questions.

### Notation Conventions

The inventory table reuses the three-state notation from `validation_report.md`'s summary determination table and adds a fourth state, `?`; the meaning has been adapted to the granularity of a discipline:

| Symbol | Meaning |
| --- | --- |
| √ | At least one model in this discipline has passed on this dimension; see the corresponding subsection |
| × | Modeling has been attempted and the evaluation process completed, but this dimension did not pass; the diagnostic record is in the corresponding subsection of `validation_report.md` |
| - | Confirmed that no evaluable object exists on this dimension, for instance the model declares no mechanism or no decision variable; this is a confirmed absence, not "not evaluated," and applies only to this specific case, not to a whole-discipline exclusion of this mode of use |
| `?` | Not yet evaluated, an independent state at the same priority as √/×/-, not a blank: the discipline direction is settled or a model file already exists, but it has not gone through the inclusion/evaluation process, and it must not be read by default as "-" or "√" |

The distinction between `?` and `-` determines how to read this table: `-` means "checked, and confirmed absent" (for example, a model declares only a static effect size and has no `equations:` block at all), while `?` means "not yet checked" (for example, a discipline already has a model that runs `--sim`/`--opt` successfully, but no one has verified whether its mechanism values match independent literature). These two are kept separate because "this discipline has no usable mechanism" and "this discipline's mechanism has not yet been verified" carry entirely different consequences; the former means this direction does not work, the latter is only a matter of remaining workload. When different models within the same row have different determinations, they are separated by "/" rather than forced into a single symbol, following the notation used in `validation_report.md`'s summary table.
