# test_fixtures Fixture Catalog

> This file is a guided tour of every YAML fixture under `models/test_fixtures/valid/` and `models/test_fixtures/invalid/`: grouped by LM format functional area (evidence, import, mc, optimization, lm_score, schedule/plan, equation, step_size, regression locks, structural validation), it explains what each file specifically tests, why it needs to be tested separately, and its relationship to neighboring files. The goal is to replace a shallow "filename plus one-line summary" index with a clear account of the design intent, so a reader can understand the full logic of this fixture set without opening each YAML individually.
>
> These files do not represent real clinical or social scenarios (as `valid/README.md` and `invalid/README.md` already note), nor are they the subject this document verifies; this document only explains "what each fixture tests and why it is designed this way," while the actual load/run assertions are the responsibility of the pytest cases under `test_verification/` (see `models/test_fixtures/README.md` for the division of roles). The engine-level pytest suite's own scope and numerical-precision verification are in the life-matters-reference-engine repository's `test_verification/verification_report.md`; literature benchmarking and optimization-plausibility verification are an entirely different matter, see [`models/test_validation/validation_report.md`](../test_validation/validation_report.md).

## 1. Evidence subtypes

`evidence_type` is the LM format's conversion layer from "a literature effect size" to "an effective value the engine can use directly," declared on a `variables:` entry (no longer a separate top-level `evidence:` block, since evidence is still fundamentally a variable, and a separate section would create two parallel namespaces, so it was folded into `variables:`, and an entry declaring `evidence_type` must have `type: parameter`). The 8 subtypes (`rr`/`or`/`hr`/`ard`/`cohens_d`/`ir`/`beta`/`pk`) each have a different conversion equation and need different auxiliary fields (`baseline_ref`, `baseline_prevalence`, `population_sd`, etc.). Testing all 8 together in one complex model would make it hard to tell, if a conversion result is wrong, whether it's a particular subtype's conversion logic at fault or the model's own dynamics equation. So each subtype first gets its own minimal file containing only "one evidence variable plus one or two display/accumulation variables" to verify the conversion in isolation, and once all pass, a comprehensive file confirms all 8 subtypes can coexist in the same model without interfering with each other.

- **`test_valid_evidence_ard.yaml`**: the absolute risk difference (`ard`) subtype, `effective = value`, needing no auxiliary field. Verifies the converted effective value can be wired in through both the `applies_to` auto-wiring path (`stroke_risk_reduction_auto`) and a hand-written dynamics path (`stroke_risk_reduction`), and that the two must match step by step, the key point for checking that "auto-wiring" and "hand-written equations" are equivalent implementation paths.
- **`test_valid_evidence_beta.yaml`**: the regression-coefficient (`beta`) subtype, likewise `effective = value`, but emphasizing that the converted annualized coefficient must correctly convert to a daily rate (divided by 365) to drive a continuous state variable (`systolic_bp`).
- **`test_valid_evidence_cohens_d.yaml`**: the standardized effect size (`cohens_d`) subtype, `effective = d x population_sd`, the only subtype that must depend on the `population_sd` auxiliary field to compute a dimensioned result, specifically testing this multiplicative conversion and unit alignment (the effect size itself is dimensionless, and multiplying by `population_sd` gives units matching the target variable).
- **`test_valid_evidence_hr.yaml`**: the hazard ratio (`hr`) subtype, `effective = baseline_ir x HR`, one of two subtypes (the other being `or`) requiring `baseline_ref` to point to an `ir` evidence entry in the same file, tested separately because "referencing another evidence entry as a baseline" has its own independent space for errors (a wrong baseline reference, mismatched units).
- **`test_valid_evidence_ir.yaml`**: the incidence rate (`ir`) subtype, `effective = value`, typically itself the baseline referenced by other subtypes, so it also needs separate confirmation that its value and units are stable when acting as "the one being referenced."
- **`test_valid_evidence_or.yaml`**: the odds ratio (`or`) subtype, whose conversion equation `effective = OR / ((1 minus p0) + p0 x OR)` is the most complex of the 8 (requiring `baseline_prevalence` p0 for a nonlinear transform), tested separately to verify this conversion step's correctness apart from the subsequent `applies_to` wiring in a minimal file.
- **`test_valid_evidence_pk.yaml`**: the PK/PD parameter (`pk`) subtype, `effective = value`, where the focus is not the conversion itself (it is already a direct value) but verifying the converted rate constant can be used directly in an hour-level-step elimination equation with no extra unit-conversion factor needed.
- **`test_valid_evidence_rr.yaml`**: the relative risk (`rr`) subtype, `effective = value`, which also compares, within the same file, "a hand-written dynamics equation multiplying an ordinary parameter baseline" against "`applies_to` auto-wired to an `ir` evidence baseline," two usages coexisting but drawing on different baselines and therefore expected not to be numerically equal, used to confirm the two paths do not accidentally share the same baseline.
- **`test_valid_evidence_types.yaml`**: a comprehensive file, verifying in one pass that all 8 subtypes can coexist in the same model, that each one's converted value does not interfere with the others, and that each can be correctly referenced by its own dynamics equation. This is the closing integration test after the isolated tests pass.

Corresponding error detection (`invalid/`):
- **`test_invalid_evidence_missing_baseline_ref.yaml`**: `rr`/`or` using `applies_to` while omitting the required `baseline_ref` — the 8 valid examples all dutifully fill in this field, and this negative case specifically confirms that when it is omitted, the loader reliably rejects it rather than silently treating the baseline as 0 or throwing an unrelated error.
- **`test_invalid_evidence_name_collision.yaml`**: now that evidence has been folded into `variables:`, the naming collision between the separate `evidence` and `variables` namespaces has structurally disappeared (only one namespace remains), so this instead verifies the accompanying new constraint, that an entry declaring `evidence_type` must have `type: parameter`; this negative case deliberately sets `type` to `state`, confirming the loader rejects it rather than silently treating a non-parameter variable as a conversion result.

## 2. Import modular composition

An LM model can compose multiple submodel files via `imports`, a typical scenario being "multiple higher-level models sharing the same base physiological component." The most error-prone part of this kind of composition is not a single file itself but **the behavior when multiple imports act together**: whether the same base component gets loaded twice when referenced indirectly through two paths, whether override priority order is correct, and whether a circular reference hangs the loader. Three positive examples form a complete two-layer-plus-diamond-dependency chain:

- **`test_valid_import_base.yaml`**: a pure component with no input at all, supplying only cardiovascular-related state variables and dynamics, specifically designed to "only be imported, never run as a standalone simulation," testing the bottom of the import chain.
- **`test_valid_import_layer.yaml`**: a middle layer, importing `base` and overriding one of its parameters (resting heart rate 65 to 58 bpm, simulating a well-trained individual), while itself also being imported by a higher-level file, creating the diamond-dependency scenario where "`base` can be indirectly referenced through two paths."
- **`test_valid_import_top.yaml`**: the top layer, directly importing both `base` and `layer` (while `layer` internally also imports `base`), verifying the loader under this diamond dependency: first, deduplicates `base` (resolving it only once, not merging its variables and equations twice); second, gets the override priority right (top layer greater than middle layer greater than base layer), so when the top layer overrides a parameter `layer` has already overridden, the top layer's value is the one that ultimately takes effect.

Corresponding error detection:
- **`test_invalid_import_circular_a.yaml` + `test_invalid_import_circular_b.yaml`**: two files that import each other, forming the simplest circular dependency. Two files are needed rather than one self-referencing file because a cycle can only be genuinely triggered, in the graph-traversal sense, by "at least two nodes pointing at each other"; these two files must exist as a pair, and loading either one alone should detect the cycle and error out the moment the other is encountered, rather than recursing infinitely or silently dropping one side of the cycle.
- **`test_invalid_import_escapes_root.yaml`**: a relative-path import that climbs one level above the `models/` root, verifying the loader enforces "an import path must stay within the models root" as a hard boundary, not merely checking whether the target file exists.

## 3. MC, Monte Carlo and probabilistic parameters

LM's probabilistic modeling has two independent layers: parameter uncertainty on the simulation side (declaring the same `parameter` as a distribution and sampling it repeatedly to get a family of trajectories) and robust optimization on the optimizer side (evaluating each candidate solution multiple times under uncertainty and taking an aggregate objective function). Both use the same distribution syntax but act on different targets, so they are verified in two separate files:

- **`test_valid_mc_distributions.yaml`**: verifies that the three distribution forms `normal()`, `uniform()`, and `lognormal()` work correctly in both "deterministic mode" (taking the distribution mean, giving a single trajectory) and "MC mode" (`runs=5`, independently resampling all three parameters 5 times each, with trajectories that should visibly diverge), while also confirming that the optimizer's Pareto front under MC mode is wider than the non-MC version because of parameter uncertainty, verifying whether "the distribution syntax itself" can be correctly consumed by both the simulator and the optimizer at once.
- **`test_valid_opt_inner_mc.yaml`**: specifically verifies `optimization.mc.runs` (inner robust optimization), where each candidate dose is repeatedly evaluated across multiple `absorption_rate` samples, and the optimizer should use the objective function averaged across runs rather than being led astray by noise from a single random sample. Distinguishing "simulation-side MC" from "optimizer-side MC" is necessary because the two answer different questions: the former answers "what does this plan's trajectory distribution look like under uncertainty," the latter answers "which plan performs best on average under uncertainty."

## 4. The optimizer's four tiers and additional mechanisms

LM's optimizer decision variables fall into four tiers by complexity, from "searching only numeric values" to "numeric values plus time/pattern/date searched simultaneously." Each tier's decoding logic (translating the optimization algorithm's internal continuous/discrete vector back into a readable dosing/training plan) is a completely different code path, so each tier is verified separately, then a combined file confirms they can be mixed within the same decision vector:

- **`test_valid_opt_t1_single.yaml`** (T1, single-variable single-objective): searches only one numeric value (protein intake), using the gradient-based solver L-BFGS-B rather than NSGA-II, verifying that this solver path itself runs end to end and constraints take effect correctly at the optimum.
- **`test_valid_opt_t1_pareto.yaml`** (T1, multi-variable Pareto): three numeric inputs plus one hard constraint (a total daily dose ceiling) plus two objectives (maximizing efficacy, minimizing toxicity), verifying that the multi-objective scenario's Pareto front shows an intuitive monotonic tradeoff, and that only solutions within the constraint boundary appear on the front.
- **`test_valid_opt_t2.yaml`** (T2, time windows): numeric values and "a specific time of day" are decision variables simultaneously, with the breakfast window discretized at hour granularity and the lunch window at 15-minute granularity, verifying that time slots of different granularity all decode back correctly to a specific clock time.
- **`test_valid_opt_t3.yaml`** (T3, weekly patterns): numeric values and "which days of the week training occurs" are decision variables simultaneously, chosen from predefined candidate day combinations, verifying the pattern index decodes back correctly to a specific combination of weekdays.
- **`test_valid_opt_t4.yaml`** (T4, start-date windows): numeric values and "which day the intervention starts" are decision variables simultaneously, verifying the date offset decodes back correctly to a specific calendar date, and that the optimizer can find the correct tradeoff between "starting earlier with a milder dose" and "starting later with a more aggressive dose."
- **`test_valid_opt_all_tiers.yaml`**: all four tiers appear together in the same 7-dimensional mixed decision vector (plus one fixed background variable not participating in optimization), the closing test verifying each tier's decoding logic does not step on another tier's dimension index, a "dimension misalignment" issue that only surfaces when multiple tiers are mixed and cannot be caught by testing each tier alone.
- **`test_valid_opt_metric_min.yaml`**: verifies `objectives[].metric: min` (the one aggregation method, among the four `final`/`max`/`min`/`mean`, not covered by any other file), using a monotonically declining inventory curve so that the objective "maximizing the historical minimum inventory" must take the trajectory's minimum rather than its final value, specifically ruling out the case where a wrong aggregation choice makes the optimization objective a misnomer.
- **`test_valid_opt_results.yaml`**: verifies a combination of three mechanisms: the optimization evaluation window is shorter than the visualization simulation window; pre-populated historical Pareto solutions under `optimization.results` are recognized on load and usable for a warm start on the frontend; and hard and soft constraints, present simultaneously, both display and take effect correctly. These three are grouped together because they all fall under "the result is not computed from scratch, but must correctly handle pre-existing state."

Corresponding error detection:
- **`test_invalid_optimization_missing_method.yaml`**: an `optimization` block declares objectives/a starting point/an algorithm but omits the required `method` field, verifying this required-field check is caught at load time, rather than only surfacing an unrelated error at actual solve time when no method can be found.

## 5. lm_score cumulative/latching semantics

**`test_valid_lm_score.yaml`**: `lm_score` has two semantics, cumulative (healthy days accrue when a metric meets target, pause during decompensation, and resume accruing once the metric returns to target) and latching (once an irreversible threshold is crossed, it is permanently zeroed, and never accrues again even if the metric later returns to normal). This file specifically verifies both semantics can coexist independently and correctly within the same hypertension-management model: blood pressure within threshold accrues healthy days; once blood pressure instantaneously crosses the stroke threshold, the latching indicator immediately and permanently freezes, but the cumulative indicator should keep accruing normally once blood pressure recovers — using the same trajectory to check both "pause/resume" and "permanent freeze," two different time semantics that do not interfere with each other, the only boundary case this field's two modes need to worry about.

## 6. Schedule / Plan time schedules and execution plans

- **`test_valid_schedules_phased.yaml`**: verifies that the two time filters `date_range` and `days` (weekday filtering) act simultaneously on a 4-phase periodized training plan (base/build/peak/taper), and that within the same step, multiple schedule entries' contributions to the same variable must correctly sum (a pulse summation) rather than overwrite each other. This verifies the combined scenario of "multiple time filters stacked," not any single filter tested alone.
- **`test_valid_plans.yaml`**: verifies that `simulation.plans` can load independently **without** a global `schedules` block: three named plans (conservative/balanced/aggressive) each define an independent caloric-deficit and exercise schedule without contaminating one another, and the union rule for `output_variables`/`output_types` takes effect correctly across multiple plans. This complements `test_valid_schedules_phased.yaml`: one tests "the stacking of multiple time filters," the other tests "isolation between multiple independent plans."
- **`test_valid_sustained_mode.yaml`**: verifies the behavior of `mode: sustained` plus `time_range`, a "sustained-window" style schedule entry (as distinct from the default single-pulse event), in an hour-step model: the default plan uses ordinary pulse events (the `--sim` baseline), while the optimizer's starting point instead uses a sustained window (`--opt`), verifying the same schedule syntax parses and executes correctly under both run modes, including a window that crosses midnight (an overnight recovery window spanning 20:00 to 08:00 the next day).

Corresponding error detection:
- **`test_invalid_date_range.yaml`**: `simulation.end_date` earlier than `start_date`. This check is deliberately not done at the structural-validation stage but deferred until a simulation/session is actually launched, so this fixture itself passes structural validation and loading normally, and only errors when `run_simulation`/`run_simulation_mc`/`start_session` is called, confirming that a runtime-context-dependent check like "date ordering" is not omitted from any call path.

## 7. Equation execution mechanics

- **`test_valid_equation_condition.yaml`**: verifies mutually exclusive branches in `equations[].condition`, two `dynamics` equations acting on the same state variable (room temperature), with mutually exclusive conditions (`< setpoint` and `>= setpoint`), simulating an on/off thermostat. The core thing being verified is "exactly one branch fires each step": neither branch may fail to fire (the state gets stuck unchanged), nor may both fire (the state gets double-updated).
- **`test_valid_equation_edge_cases.yaml`**: covers several edge-case expression forms that are easy for the engine's expression-evaluation path to miss: a chained comparison nested in a ternary expression (`1.0 if 0 < level < 10 else 0.0`), `and` short-circuit evaluation guarding a division (avoiding division by zero), and an equation deliberately designed to trigger a `ZeroDivisionError` at some step, used to verify the engine catches an evaluation exception on a single equation per-step and freezes it at its last successfully computed value (without crashing the whole simulation or letting NaN/inf silently propagate downstream). This file also records an execution-order detail no test had explicitly verified before: within the same step, equations execute in descending `priority` order, and a higher-priority equation reads a lower-priority equation's value **before it is updated this step** — this is not a past defect but established behavior of the current execution model, worth recording separately as documentation for any future model design that depends on equation execution order.

Corresponding error detection:
- **`test_invalid_equation_undefined_var.yaml`**: a `dynamics` expression references a never-declared variable, verifying that AST-based undefined-variable detection catches this kind of typo or missing declaration at load time, rather than only surfacing a harder-to-locate error at runtime when the variable cannot be found.
- **`test_invalid_equation_deprecated_dt.yaml`**: a `dynamics` expression uses the deprecated symbol `dt` instead of the current `step`, verifying the validator actively rejects the old symbol rather than silently tolerating it and letting old and new notation mix with inconsistent unit meaning.

## 8. Step size and cross-scale consistency

LM allows different models to each run at a different `step_size` (minute/hour/day), and allows one model to import another that uses a different step size. The most common errors in this kind of cross-scale composition are "an equation missing a multiplication by `step` where it needs one, or multiplying by it where it shouldn't," and "a higher-level model's step size accidentally contaminating the step size an imported component should preserve."

- **`test_valid_step_hour.yaml`**: an end-to-end hour-level-step verification, a single-compartment PK model with oral dosing at a fixed time each day, 30 days/720 steps, verifying that plasma concentration shows a "daily peak then decay" pattern and settles into a periodic steady state within a few days; also verifies that the Nelder-Mead single-objective solver, an alternative solve path to NSGA-II, converges correctly.
- **`test_valid_step_minute.yaml`**: a minute-level-step verification, three meals a day, 3 days/4320 steps, verifying that schedule entries fire correctly at sub-hour precision, that the basal-metabolism clearance equation correctly multiplies by `step` (a rate quantity) while the meals' pulse inputs do not multiply by `step` (an instantaneous quantity), and that the `output_types: [state, input]` filter outputs only the specified variable types.
- **`test_valid_step_cross_import_base.yaml`** + **`test_valid_step_cross_import_top.yaml`**: the core cross-scale consistency check — `base` runs at a day-level step, with body weight decaying exactly 1% each day, giving a known analytical trajectory (day0 to 100.0, day1 to 99.0, day2 to 98.01, day3 to 97.03); `top` runs at an hour-level step and imports `base`, verifying that `base`'s internal daily-decay equation still fires only once per 24-hour boundary, and that when it fires, it matches exactly the analytical trajectory of `base` run independently — it must neither fire erroneously every hour just because it is imported by an hour-level model (a 72-fold overcount), nor fail to fire at all because of the step-size mismatch in the other direction. `top` itself has a separate, independent hour-level PK variable that simultaneously verifies the hour-level engine itself works correctly, providing cross-confirmation without interfering with the cross-scale day-level variable.
- The Banister step-convergence series (`test_valid_banister_v1_analytical.yaml` and its 5 step-size variants `_step_{12h,6h,3h,1h,30min}.yaml`) are likewise step_size-related fixtures, but their purpose is numerical-precision step-convergence testing (protocol V4), not the structural "is the cross-scale composition correct" question discussed in this section; the complete methodology and current execution results are in the life-matters-reference-engine repository's `test_verification/verification_report.md`, section 2, not repeated here.

Corresponding error detection:
- **`test_invalid_step_size.yaml`**: `simulation.step_size.value` is 0, verifying the validator requires the step size to be a positive number, avoiding downstream consequences like division by zero or an infinite loop.

## 9. Regression-lock fixtures

The following two files do not correspond to a "new feature" but pin down, with a minimal model, a specific behavior previously found to be a problem, preventing a future change from unintentionally breaking that same behavior again. Both are written the same way as an ordinary valid fixture (structurally valid, loads and runs normally), except the point of the assertion is "a specific number must exactly equal the expected value," not "is the structure or feature usable."

- **`test_valid_pulse_reset_bounds_floor.yaml`**: verifies that when an input variable with a lower bound greater than 0 (`bounds[0] > 0`) fires a pulse event, the value read must exactly equal the `value` declared in the schedule, not `bounds[0] + value`. A variable of this kind is reset to zero at the start of every step, then has the current triggering event's contribution added; this file pins down that this "reset to zero" step must not be affected by the lower-bound clamping logic, otherwise every trigger would be contaminated by the lower-bound value, and a variable with a higher lower bound would suffer this problem more severely.
- **`test_valid_same_day_duration.yaml`**: verifies that when `start_date == end_date` (a simulation window of a single calendar day), the simulation must cover the full 24 hours, rather than degenerating into a 0- or 1-hour stub window. This kind of edge case is easy to overlook in an implementation that "computes total duration from the date difference," since the date difference for the same day is 0, and without special handling, a schedule event later in the day (this fixture sets one at 18:00) would never fire.

## 10. Structural error detection (invalid items not falling under the areas above)

**`test_invalid_yaml_not_dict.yaml`**: the top-level YAML content is itself a list, not a mapping. This is the precondition for every other validation to take effect: the loader must first confirm that `yaml.safe_load()` returns a dict before parsing fields such as `variables`/`equations`/`imports` further down; without this defensive check, top-level content that is a list or a scalar would throw a confusing `AttributeError` deep in the parsing code, rather than a clear error message pointing at the root cause. This is the only fixture that does not belong to any functional area above, instead protecting the precondition for "whether every other validation can even begin."

## Adding a new fixture

Which functional-area category to add a new fixture under, along with the specific steps and naming convention, are in `valid/README.md` (positive examples) and `invalid/README.md` (negative examples, including a checklist for "adding a new error-detection case"). After adding one, add a corresponding note in this file's matching section explaining what it tests, why it needs separate testing, and its relationship to existing files in the same section, rather than just adding a line to the filename list.
